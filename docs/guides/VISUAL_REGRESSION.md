# 📸 Visual Regression Testing

Visual regression tests catch changes that behavioral tests can't: a button
that still works correctly but has drifted three pixels to the left, a CSS
change that broke a layout on one specific page, a font that silently
stopped loading. Testbook's functional E2E suite (`tests/e2e/`) verifies
that clicking things does the right thing. This suite verifies that the
page still *looks* right.

This is infrastructure-first content. A prior pass evaluated adding
screenshot tests and correctly deferred: screenshot comparisons are the
most failure-prone kind of test this repo could add, and adding them
without deciding how baselines get managed first would have produced a
flaky, ignored test suite. This document explains the infrastructure
decisions made to avoid that, including a real one found while building
it, not just the tests themselves.

## Why this runs separately from the main test suite

`.github/workflows/visual-regression.yml` runs on a weekly schedule
(Monday 6am UTC) and on manual `workflow_dispatch` - it is **not** wired
into `testbook-ci.yml` or `full-checks.yml`, and does not run on every
push or pull request.

Screenshot comparison is inherently more brittle than a behavioral
assertion. A 2% pixel-difference threshold (configured in
`tests/playwright.visual.config.js`) absorbs minor antialiasing noise, but
it can't absorb everything: a font rendering difference between two
supposedly-identical runner images, a genuinely unrelated design tweak
landing in the same PR, or - as this pass found firsthand - nondeterministic
seed data producing a different but equally valid page. Gating every PR on
that risk would mean either training the team to click "re-run" on red CI
without looking (defeating the point of CI) or spending review time
investigating failures that turn out to be nothing. A weekly cadence still
catches a real regression within days, and `workflow_dispatch` means a
baseline update after an intentional design change doesn't have to wait
for Monday.

## Why the CI runner version is pinned

The job runs on `ubuntu-22.04`, not `ubuntu-latest`. This matters more here
than in any other workflow in this repo: `ubuntu-latest` is a moving
target - GitHub periodically retargets the label to a newer image - and
font hinting, antialiasing, and subpixel rendering can all shift slightly
between OS image versions. A baseline captured on one image version
compared against a run on a different one would produce diffs that have
nothing to do with the application changing. Pinning the exact version
means a baseline stays valid until *this workflow file* is deliberately
updated to a newer pin, which is a decision someone makes on purpose, not
something that happens silently on GitHub's schedule.

This also means the baselines are tied to Linux/Chromium rendering
specifically. Playwright's snapshot filenames encode the platform
(`feed-page-chromium-linux.png`), so a screenshot captured on a
contributor's Mac or Windows machine locally will not match - and should
not be committed as - the baseline CI compares against. Baselines for this
repo are only ever generated by the pinned CI runner (see below), never
captured locally and committed by hand.

## Bootstrapping: this repo does not ship baselines yet

Because of the platform constraint above, and because generating a real
`ubuntu-22.04` baseline requires actually running the pinned CI
environment (not something reproducible from a contributor's own
machine), this pass adds the visual test suite and the CI infrastructure
to run it, but does **not** commit baseline screenshots. `tests/visual-snapshots/`
does not exist in the repository yet.

The three tests in `tests/visual-tests/` were run and verified locally
(on macOS, three consecutive clean comparisons against a locally-generated
baseline) to confirm the test logic itself - navigation, wait conditions,
masking, database reset - is sound and deterministic. That verification is
real, but it is not the same thing as a Linux CI baseline, and the two
should not be conflated.

**Before the weekly schedule will produce a meaningful pass/fail signal**,
a maintainer needs to run the bootstrap step described below once. Until
then, the first scheduled run (or any `workflow_dispatch` run without
`update_baselines`) will fail with "no baseline found" for all three
tests - that failure is expected, not a bug report.

## How to update baselines intentionally

Use this after either bootstrapping the suite for the first time, or after
a real, intentional design change that should update what "correct" looks
like.

1. Go to the **Actions** tab, select **Visual Regression**, click
   **Run workflow**.
2. Check the **update_baselines** input, then run it.
3. The run generates fresh screenshots on the pinned `ubuntu-22.04`
   runner instead of comparing against the old ones, and uploads them as
   a `visual-regression-baselines` artifact - it does not commit anything
   automatically.
4. Download the artifact and look at every image before committing
   anything. Specifically check: does the diff (if you're updating
   because of a real change) match the change you intended, and only
   that change? Is any part of the page you weren't expecting to change
   actually different (a sign something else - a data seeding issue, a
   layout regression - is also happening)?
5. Once satisfied, copy the artifact's contents into
   `tests/visual-snapshots/` in your working tree and commit them
   normally, in their own commit, with a message describing *why* the
   baseline changed (e.g. `chore(visual): update feed baseline for new
   post-card padding`), not just that it did.

Never run `--update-snapshots` locally and commit the result - see the
platform note above for why that baseline would be silently wrong for CI.

## What a real visual regression failure looks like

While verifying the feed page test during this pass, it failed on a
second run against its own freshly-generated baseline - both runs used
identical database resets, no code changed in between, and yet the diff
tool reported a 3% pixel difference (above the 2% threshold), concentrated
in the second post in the feed.

Reading the actual diff artifact (`tests/test-results/.../feed-page-diff.png`,
uploaded automatically on failure - the same path CI uploads under
`visual-regression-diffs`) showed the highlighted region wasn't a
rendering glitch: it was a genuinely different repost. One run's feed
showed "Sarah Johnson reposted... Mike Chen: Made it to the summit!"
in that position; the other showed "James Taylor reposted... Lisa
Williams: Morning workout done!" - different users, different content,
same position.

The root cause was in `backend/seed.py`, not in the test: repost
timestamps were generated with `timedelta(hours=random.randint(1, 24))`,
so the feed's `ORDER BY created_at DESC` genuinely produced a different,
equally-valid order on every single database reset. That's real
nondeterminism in what the app rendered, not a test bug - fixed by making
those timestamps fixed values instead of random ones (same commit as this
document), after which three consecutive runs produced byte-identical
comparisons.

This is worth reading closely because it's the realistic failure mode for
this kind of test: the diff image and pixel-difference percentage are
almost never enough on their own. Reading *what* changed in the image -
not just that something did - is what tells you whether you're looking at
a real regression, a flaky rendering artifact, or (as here) a data
determinism bug the screenshot test happened to be the first thing to
notice.

## What should and should not be caught here

**Good fit:**

- Layout breaking on a specific page (elements overlapping, content
  overflowing its container)
- A CSS change that was scoped to one component but affected another
- A missing image, icon, or avatar where one should render
- Text that no longer fits its container and gets clipped or wraps
  unexpectedly

**Not a good fit - don't try to make these tests catch:**

- Anything already covered by a faster, more specific assertion. If a
  test can check `expect(errorMessage).toContainText(...)`, that's a
  better test than a screenshot that happens to include the error message
  - it's faster, it doesn't break on unrelated pixel changes nearby, and
  its failure message tells you exactly what's wrong instead of "here's a
  diff image, go look."
- Cross-browser rendering differences. This suite is Chromium-only,
  deliberately (see `playwright.visual.config.js`) - Firefox and Safari
  render text and gradients slightly differently in ways that are
  correct, not regressions, and mixing that into a single tolerance
  threshold would make the threshold meaningless for everything else.
- Content that's expected to vary (timestamps, anything with real
  randomness). Mask it (`mask: [...]` in `toHaveScreenshot()`, used in
  `feed.spec.js` and `post-detail.spec.js` for post/comment timestamps)
  rather than accepting a wider pixel-difference tolerance for the whole
  page, which would also hide real regressions elsewhere on that page.
- Anything that legitimately differs between environments this suite
  doesn't control for (a locale-dependent date format, a user's system
  font substitution) - fix the underlying nondeterminism the way the
  repost-timestamp bug above was fixed, don't paper over it with a looser
  threshold.
